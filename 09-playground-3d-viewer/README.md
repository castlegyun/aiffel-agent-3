# 놀이터 3D 뷰어

폰으로 찍은 8초 영상에서 동네 놀이터를 3차원 알갱이(가우시안 스플랫) 장면으로 만들고, 브라우저에서 돌려 볼 수 있게 올린 과제입니다.

- 뷰어 주소(Pages): https://castlegyun.github.io/aiffel-agent-3/09-playground-3d-viewer/
- 장면 파일 직접 확인: https://castlegyun.github.io/aiffel-agent-3/09-playground-3d-viewer/scene.sog
- 화면 갈무리: `shots/viewer.png`

```
09-playground-3d-viewer/
├── index.html      three.js + Spark 2.4.0 뷰어
├── scene.sog       줄인 알갱이 파일 (11.98 MB)
├── README.md       촬영과 측정 결과 (이 문서)
└── shots/viewer.png
```

## 1. 공개 판단

누구나 드나드는 동네 공공 놀이터(야외)라서 공유해도 된다고 판단했습니다. 사람은 한 명이 멀리 작게, 뒷모습으로만 찍혀 얼굴을 알아볼 수 없습니다. 안내판과 주차된 자전거·오토바이가 멀리 보이지만, 내가 확인한 프레임과 뷰어 화면에서는 글자나 번호판을 읽을 수 없는 크기입니다.

## 2. 촬영

| 항목 | 값 |
|---|---|
| 찍은 곳 | 동네 놀이터 (미끄럼틀, 시소, 그네, 정자) |
| 영상 | 8.1초, 1280×720, 약 29.8프레임/초 |
| 걸은 경로 | 놀이터 앞에서 옆으로 움직이며 미끄럼틀·정자와 그네·시소 쪽을 차례로 담음 (프레임 1번 → 24번) |
| 추출한 프레임 | 24장을 고르게 뽑아 긴 변 1024로 줄임 (1024×576) |
| 복원 모델 | MapAnything `facebook/map-anything-apache`, Colab T4, fp16 |

영상은 메신저(텔레그램 폴더)를 거쳐 받은 파일이라 한 번 더 압축됐을 수 있습니다(추측: 파일 위치만 보고 한 판단). 권장 길이 15~20초보다 짧게 찍었습니다.

## 3. 복원 결과와 카메라 퍼짐

| 항목 | 값 |
|---|---|
| 점(알갱이) 개수 | 2,662,379 |
| 카메라 퍼짐 비 | 0.125 (카메라 위치 상자 대각선 ÷ 장면 상자 대각선) |
| 복원 시간 | 8.9초 |
| 최대 GPU 메모리 | 6.97 GB |

위에서 본 그림에서 추정된 카메라 위치는 한곳에 모이지 않고 옆으로 길게 이어졌습니다. 다만 걸은 방향과 거리를 줄자로 잰 것이 아니라서, 실제 이동 경로와 방향까지 정밀하게 대조하지는 못했습니다. 퍼짐 비는 합격선이 아니라 보조 값으로만 봤습니다. 장면의 가장 긴 변은 약 33.5(모델이 낸 미터 단위 추정이며 실제 치수를 잰 값이 아닙니다)입니다.

## 4. 형식별 크기 (같은 PLY를 변환)

변환 도구는 `@playcanvas/splat-transform@3.10.3`입니다. 알갱이 개수는 변환한 파일을 다시 PLY로 되돌려 머리글에서 읽었고, 네 형식 모두 같았습니다.

| 파일 | 크기(바이트) | 크기(MB) | 변환 시간(초) | 알갱이 개수 | 알갱이당 바이트 |
|---|---:|---:|---:|---:|---:|
| scene.ply (원본) | 181,042,189 | 172.66 | - | 2,662,379 | 68.0 |
| scene.compressed.ply | 43,347,526 | 41.34 | 8.1 | 2,662,379 | 16.3 |
| scene.spz | 20,894,289 | 19.93 | 7.6 | 2,662,379 | 7.85 |
| **scene.sog (사용)** | **12,566,359** | **11.98** | 17.9 | 2,662,379 | **4.72** |

- 원본 PLY가 알갱이당 68바이트인 것은 값 17개(위치 3, 법선 3, 기본 색 3, 불투명도 1, 크기 3, 회전 4) × 4바이트이기 때문입니다.
- 형식을 바꿔도 알갱이 수는 그대로입니다. 줄어든 것은 파일 크기이고, 화면을 그리는 부담은 같습니다.
- 뷰어에서 직접 열어 본 것은 `.sog`뿐입니다. 나머지 세 형식은 크기만 비교했고 화면은 비교하지 못했습니다. `.sog`를 고른 이유는 가장 작고, 쓰는 뷰어(Spark 2.4.0)에서 열렸기 때문입니다.
- 알갱이 크기 규칙은 반지름 = K × 장면의 가장 긴 변 ÷ √N, K = 1.4, 불투명도 0.9입니다. 평가용 사진을 따로 빼지 않아서 PSNR·SSIM·LPIPS는 재지 않았습니다.

## 5. 첫 화면까지 걸린 시간

| 기기 | 통신 | 첫 화면까지 | 파일 받는 데 |
|---|---|---|---|
| 내 컴퓨터 (같은 컴퓨터의 로컬 서버) | 인터넷 아님 | 재지 않음 | 0.27초 |
| 내 컴퓨터 (공개 주소, 자동 브라우저로 폰 너비 화면) | 인터넷 | 재지 않음 | 0.95초 |
| 내 폰 (갤럭시 26+) | 와이파이 | 0.38초 (폰에서 직접 열어 본 값) | 너무 빨라서 따로 재지 못함 |
| 다른 사람 기기 (갤럭시 20+,노트북) | 와이파이 | 열림 확인, 빠르게 열림 | 2초,7초 |

- 내 폰에서는 공개 주소의 화면이 뜨고, 주소 뒤에 `/scene.sog`를 붙이면 파일이 내려오는 것까지 확인했습니다.
- 다른 사람의 기기(갤럭시 20+,노트북/ 와이파이)에서도 공개 주소를 열어 화면이 뜨는 것을 확인했고 빠르게 열렸습니다 다운로드도빨랐습니다. 
- 이미 파일을 받은 기기와 처음 받는 기기는 조건이 다를 수 있습니다. 위 값은 와이파이에서 본 것이라 LTE 같은 다른 통신 환경에서는 달라질 수 있습니다.
- 내 컴퓨터의 로컬 값은 인터넷을 거치지 않은 값이라 폰 값과 비교할 수 없습니다.

## 6. 잘 보이는 방향과 안 나온 자리

뷰어를 직접 돌려 보며 확인했습니다(`shots/viewer.png`는 처음 열린 시점).

**잘 보이는 곳**: 촬영한 위치 근처에서 정자, 그네, 바닥 타일이 알아볼 만하게 나옵니다.

**안 나오거나 무너지는 곳과 이유** (이유 중 "추측"은 직접 확인하지 못한 해석입니다)

| 보이는 모습 | 이유 |
|---|---|
| 하늘과 먼 배경이 검게 비어 있음 | 아주 먼 곳은 옆으로 움직여도 사진 속에서 거의 안 움직여(시차가 거의 없어) 거리를 알기 어렵습니다. 추측: 모델이 믿기 어려운 곳을 점으로 만들지 않고 제외한 것으로 보입니다. |
| 정자 지붕 아래, 나뭇가지 사이, 물체 가장자리에 검은 틈 | 앞뒤 물체의 경계에서는 깊이가 크게 바뀌어 점이 불안정합니다. 추측: 가장자리 점을 지우는 설정(`mask_edges`)이 틈을 만든 것으로 보입니다. |
| 시소와 미끄럼틀이 뭉개지거나 겹쳐 보임 | 가까운 물체는 시차가 커서 사진마다 위치 차이가 큰데, 앞 물체가 뒤를 가려 짝을 맞추기 어렵습니다. 추측: 사진마다 깊이의 크기가 조금씩 어긋나 점이 두 겹으로 놓인 것으로 보입니다. |
| 옆이나 아래에서 보면 장면이 얇은 판처럼 보이고, 놀이기구 뒤쪽이 비어 있음 | 찍은 쪽에만 점이 있고 뒤쪽 면은 한 번도 찍지 않았습니다. 알갱이를 키워도 찍히지 않은 면은 생기지 않습니다. |
| 위에서 내려다보면 바닥이 줄무늬처럼 길게 늘어남 | 추측: 깊이 오차가 카메라가 바라본 방향으로 퍼지고, 알갱이 크기를 한 가지 규칙(K = 1.4)으로만 정해 방향마다 맞지 않기 때문으로 보입니다. |

영상이 8.1초로 짧아 여러 방향에서 본 사진이 적었고, 이것이 위 문제를 키웠을 수 있습니다(추측). 개선하려면 안 찍힌 면은 다시 촬영하고, 알갱이 사이 틈은 크기를 조절하며, 움직임이 느리면 `N_KEEP`으로 점 수를 줄여 비교합니다.
